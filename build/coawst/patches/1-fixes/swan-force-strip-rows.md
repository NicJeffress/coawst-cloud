## In short

SWAN can write the wave-driven force (`FORCE`: the force per unit area that
breaking and shoaling waves exert on the water column, x and y components)
as BLOCK output on its computational grid. On several SWAN processes that
output had a whole grid row (or column) missing at every boundary between
two processes' strips. With 4 processes on a 76-row grid, rows 19, 38 and 57
held the exception value. The force itself was fine. The point had been given
to a process that could output Hs-based quantities there but not `FORCE`.
It is an output bug only: the waves, the fields sent to ROMS and every other
output were right.

Found 2026-10-31 while testing `swan-periodic-curvilinear`. It happens on
regular grids too, periodic or not, with or without the engine's patches.
That test had only compared values where both runs had them, so it never
flagged the missing points.

## Background: how a parallel SWAN run writes BLOCK output

SWAN splits the grid into strips, one per process, along its longer
direction. Each process computes its own strip, and also keeps copies of the
3 rows next to it in each neighbour's strip (the halo), which are exchanged
during the computation. For output:

1. Every process computes the output quantities at the points it owns
   (`SWOEXC` marks them in `IONOD`) and writes them to its own temporary
   file.
2. At the end of the run the master process merges the files (`SWCOLBLK`):
   for each point it takes the value from the process that a global map,
   `BLKND`, names for it.

Both steps turn a point's computational-grid coordinate `XC` (0 for the
first grid line, 1 for the second, ...) into a grid index (1, 2, ...). They
did it with

```fortran
IX = INT(XC(IP))
IF ( .NOT.EQREAL(XC(IP),RVAL1) .OR. EQREAL(XC(IP),0.) ) IX = IX + 1
```

which adds 1 when `XC` is between grid lines or exactly 0, but not when it
is a whole number other than 0. A point on grid line k (k > 0) therefore got
index k instead of k+1: one row off. (One output type, `BLKV`, always added
1 in `SWOEXC`, but not in `SWCOLBLK`.) The two steps agree with each other,
so every point was still written exactly once. But the first row of each
strip was written by the process below, which holds it as its first halo row.

For most quantities that makes no difference. They are interpolated from
the action density, which is exchanged into the halo, and Hs and the others
came out identical to a single-process run. `FORCE` (`SWOEXF`) differs: it
is the gradient of the radiation stress, so it needs the rows either side of
the point. It also skips any point whose neighbours have zero Hs or no
depth, using Hs from the computation (`COMPDA`). That Hs is only filled in
up to the first halo row. One row further, in the second halo row, it is 0,
so the process wrote the exception value for the whole row.

## block_point_owner: the change

A BLOCK point on grid line k now gets index k+1, in both steps:

```fortran
!  SWOEXC (swanout1.ftn): which points this process outputs
!           swan-force-strip-rows (block_point_owner): a BLOCK point on
!           grid line k (0-based) is index k+1, as SWCOLBLK takes it
            IF ( .NOT.EQREAL(XC(IP),RVAL1) .OR. EQREAL(XC(IP),0.) .OR.
     &           RTYPE(1:3).EQ.'BLK' ) IX = IX + 1
!           (and the same for IY; before: RTYPE.EQ.'BLKV')

!  SWCOLBLK (swanparll.ftn), both places: which process file a point comes from
!              swan-force-strip-rows (block_point_owner): a point on
!              grid line k (0-based) is index k+1, as in SWOEXC
               IXK = IXK + 1
               IYK = IYK + 1
!           (before: the same conditional +1 as above)
```

Each point is now written by the process whose strip contains it, and
`FORCE` needs at most the first halo row, where Hs is set. Points between
grid lines (FRAME output) are mapped as before. TABLE and spectral output,
which have their own merge routines with the same rule, are not changed.

## How the test works

`tests/fixes/swan-force-strip-rows/run.sh`
([README](../../../../tests/fixes/swan-force-strip-rows/README.md)) builds
COAWST's Inlet_test before and after the patch (the fixes before it in the
series, and up to it). Inlet_test is a coupled ROMS + SWAN case with a 77 x
72 curvilinear grid, not periodic. Each build runs 1 h on 1, 2 and 3 SWAN
processes, with `FORCE` added to the case's BLOCK output (`.mat`, every
30 min). The checker compares `FORCE` on 2 and 3 processes with 1 process,
every other `.mat` output and `FORCE` on 1 process before and after, and
the ROMS history before and after.

## Engine test results

Run 2026-10-31 on the control VM. PASS.

| Check | Before the patch | After the patch |
|---|---|---|
| `FORCE`, 2 SWAN processes vs 1 | column 39 missing (280 values); equal elsewhere | identical, nothing missing |
| `FORCE`, 3 SWAN processes vs 1 | columns 26 and 52 missing (536 values) | identical, nothing missing |
| 24 other `.mat` outputs (depth, Hs, dissipation, ...) on 1, 2, 3 processes; `FORCE` on 1 | | bit-identical to before |
| ROMS history, 1, 2, 3 SWAN processes | | bit-identical to before |

Inlet_test's grid is longer in x, so SWAN splits it into column strips and
the missing lines are columns.

With the whole series (standalone periodic reef of
`tests/improvements/swan-periodic-curvilinear`, 100 x 76 grid, row strips),
`FORCE` on 4 processes equals 1 process on the stretched curvilinear grid
and on the uniform regular one. Before, rows 19, 38 and 57 were missing.
The 1-process `FORCE` is unchanged.

## Who is affected

Anyone using SWAN's BLOCK output of `FORCE` from a run with several SWAN
processes (most coupled runs): the output had a line of exception values at
every strip boundary, so maps of the wave force had gaps, and derived
quantities (for example averages along a line) were wrong there. The waves,
the coupling to ROMS and all other outputs were not affected.
